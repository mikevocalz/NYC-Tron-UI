## Concrete changes

The kitchen now reuses the existing shared maestroSessionLimits.driverStartupMs=180000. [Pinned LocalXCTestInstaller](https://github.com/mobile-dev-inc/Maestro/blob/67d8a677029261fa424a45a10d08eacd6aa0deed/maestro-ios-driver/src/main/kotlin/xcuitest/installer/LocalXCTestInstaller.kt) accepts MAESTRO_DRIVER_STARTUP_TIMEOUT and otherwise uses120000. The kitchen environment and version diagnostic record the shared180000 setting. This aligns bounded startup behavior with the existing native runner; it does not waive driver readiness.

The iOS workflow installs the SHA-verified pinned Maestro after Java/Node setup and executes its exact-version preflight before expensive app compilation or simulator boot. The existing post-install/post-boot native-proof version verification stays strict. Early initialization is fail-fast measurement and dependency warmup, not a proven timeout repair. [Pinned App.kt](https://github.com/mobile-dev-inc/Maestro/blob/67d8a677029261fa424a45a10d08eacd6aa0deed/maestro-cli/src/main/java/maestro/cli/App.kt) initializes logging, analytics/dependencies and command infrastructure before printing version. [Dependencies.kt](https://github.com/mobile-dev-inc/Maestro/blob/67d8a677029261fa424a45a10d08eacd6aa0deed/maestro-cli/src/main/java/maestro/cli/Dependencies.kt) unpacks embedded dependencies without needing a running app/simulator.

A CI-only early helper exclusively creates kitchen-maestro-preflight output. Both early and post-boot calls instrument the existing synchronous exact-version verifier through one guarded watcher per probe. The watcher runs only on hosted Darwin with pinned Java and output inside RUNNER_TEMP; child mode validates the same output/CI guards and a safe-integer parent PID greater than1. No static circular import or duplicate watcher is introduced. At40seconds an owned Node watchdog captures process PID/PPID/CPU/memory/RSS/executable columns without environment or argument columns. It uses the pinned JAVA_HOME jcmd to identify only exact maestro.cli.AppKt processes descended from this preflight, then captures at most one owned JVM thread dump. The raw JVM discovery list is never persisted. Every diagnostic process has a5second timeout,64KiB capture ceiling and32KiB retained stream ceiling. Failed version checks retain existing bounded diagnostics. Finally the verifier synchronously kills its exclusively owned detached POSIX process group, including any in-flight ps/jcmd child. This prevents orphaning a diagnostic child and losing its timeout timer. The version API remains synchronous; cleanup neither extends nor replaces its60second cap. The separate preflight artifact uploads with always(), including failure.

The60second version cap, exact2.12.1 stdout comparison, archive pin/SHA,600second flow cap, fresh drivers, exact runtime/JUnit identity, both import modes, all27assertVisible blocks per mode and current PNG/provenance gates are unchanged. No retry added; no app/API/window/orientation or local device interaction.
