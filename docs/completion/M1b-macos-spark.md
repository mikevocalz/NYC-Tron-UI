# M1-b spike — @nyc-tron/ui components on a real Spark (react-native-macos) host

Status: spike report with runtime evidence. This document records what ran on
a real macOS AppKit-backed RN runtime. It changes no product code, promotes no
`acceptance` field and certifies no platform; `platformEvidence.macos` stays
absent — this is a dev-Runner host rendering RN-view components, not a shipped
adapter.

Machine: macOS 27.0 (26A428), Apple M3 Pro, arm64. Spark `@legendapp/spark`
0.0.3 (RN 0.83.10 / react-native-macos 0.83.0 / Expo 55.0.32 / React 19.2.0),
the version matrix M1-a verified.

## 1. What was built

A Spark app at `tooling/spike/m1b-macos-spark/TronSparkApp/` — a separate npm
project with its own lockfile, fully outside the repo's pnpm workspace (the
repo's Expo 58 / RN 0.88 graph cannot share a host with Spark; M1-a §1).

- Scaffolded by `npx spark create TronSparkApp --platform macos`.
- `package.json` carries the M1-a autolinking workaround:
  `expo.autolinking.exclude = ["react-native-windows"]` — without it
  `spark dev` dies in Expo autolinking because RNW 0.83.2's config probes for
  `pwsh.exe` (`spark build` applies this itself; `spark dev` does not).
  Confirmed still required on 0.0.3.
- `src/nyc-tron/` holds **verbatim** copies of real product sources from
  `packages/ui/src/components/` at commit `8410e43` (see
  `src/nyc-tron/PROVENANCE.md`): `Button.tsx`, `SegmentedControl.tsx`,
  `Card.tsx`, `TextField.tsx`, `styles.ts`, `forms/choice-keys.ts`. Zero edits —
  every compatibility measure lives in the host app, per the workstream
  constraint.
- `App.tsx` renders those four components plus, for contrast, Spark's own
  `SegmentedControl` from `@legendapp/spark/ui` (which resolves to
  `NativeSegmentedControl` → `RNNativeSegmentedControl.mm` → a real
  `NSSegmentedControl`, per M1-a §2a).
- `global.css` + `uniwind` + `tailwindcss` supply the app-owned theme. This is
  the key compat finding: **uniwind works on Spark**. It is build-time only
  (Tailwind 4 + lightningcss via Metro transform, no native module), peer range
  `react-native >=0.81` covers 0.83, and its `withUniwindConfig` wrapped the
  `expo-desktop-metro-config` output cleanly. The vendored components'
  `className` recipes (`bg-primary`, `rounded-control`, `min-h-11`, …)
  therefore render with their real Tailwind styling — the app supplies only
  the `@theme` tokens, exactly the AGENTS.md rule-2 contract. `uniwind-types.d.ts`
  was generated by the Metro run.

## 2. Commands that ran

```sh
cd tooling/spike/m1b-macos-spark
npm i @legendapp/spark@0.0.3
npx spark create TronSparkApp --platform macos
cd TronSparkApp
# package.json: add expo.autolinking.exclude=["react-native-windows"]
npm i uniwind@1.13.2 tailwindcss@4     # already in committed package.json
npx spark doctor                        # "Dependency pins match… Native toolchain available."
npx spark dev --no-open                 # Metro on 127.0.0.1:8081
```

`spark dev --no-open` waits for a launch key and this session was not a TTY, so
the Spark Runner was launched directly — the same thing `spark dev` does
internally (`spark-cli/dist/dev.js` → `launch()`):

```sh
RUNNER=~/.spark/downloads/0.0.3/<hash>/SparkRunner.app/Contents/MacOS/SparkRunner
SPARK_WINDOW_CONFIG='{"size":{"width":1000,"height":700},"restoreBounds":true}' \
SPARK_PROJECT_ID=<extra.spark.projectId> SPARK_PROJECT_NAME=TronSparkApp \
SPARK_PROJECT_VERSION=0.0.1 \
SPARK_BUNDLE_URL='http://127.0.0.1:8081/index.bundle?platform=macos&dev=true&minify=false' \
"$RUNNER" -RCT_jsLocation 127.0.0.1:8081 &
```

Metro bundled `index.ts` → **956 modules, platform=macos** (up from the 752 in
the bare template; uniwind + vendored TSX included, no resolution errors).

## 3. Evidence

- `evidence/m1b-spark-window.png`, `-live.png`, `-full.png`,
  `-final.png` — `screencapture -x -l<CGWindowID>` of the real
  `TronSparkApp` window (1000×700 pt). Pixel histogram of the first capture
  shows the actual theme tokens rendered: `#101017` app background,
  `#20202C`/`#17171F` Card surfaces, `#B2A7FF`→`(176,167,249)` primary
  Button fill, `#FB7185`→`(234,121,135)` danger Button, `#F6F6FD` text —
  i.e. uniwind resolved the components' real className recipes, not a
  fallback.
- `evidence/m1b-ax-tree.txt` — NSAccessibility dump of the window's scroll
  area via System Events. It lists, side by side:
  - NYC-Tron `SegmentedControl` segments as `AXUnknown … "radio button,
    checked/unchecked"` (RN views exposing the component's `role="radio"`
    semantics — these are **RN-view components, not AppKit controls**);
  - Spark's native control as `AXRadioGroup "Spark native segmented control"`
    with three `AXRadioButton` children — the real `NSSegmentedControl`;
  - NYC-Tron `Button`s as `AXButton` with accessible names
    Primary/Secondary/Ghost/Danger/Disabled, `Loading` showing `busy` plus a
    live `AXBusyIndicator`;
  - NYC-Tron `TextField` as `AXTextField "Notes"`.
- **Interaction roundtrip (the strongest evidence):** `AXPress` on the Spark
  `AXRadioButton "Preview"` fired `onValueChange` → React `setMode` → the
  NYC-Tron `SegmentedControl` re-rendered: post-press AX dump shows
  `tron Preview = radio button, checked` while `tron Design/Handoff` went
  unchecked, and the native group mirrors `Preview = 1`. A real AppKit
  control drove real NYC-Tron component state.
- **Fast Refresh:** editing `App.tsx` title and saving produced a live
  re-render — pixel diff vs. prior capture: 14,903 changed px confined to
  the title bbox (718,204–1372,255).

## 4. Compat matrix — what ported verbatim vs. what needs shims

Ported with **zero source changes** (pure `react` + `react-native` imports):

- `Button`, `Card`, `SegmentedControl`, `TextField`, `styles.ts`,
  `forms/choice-keys.ts`. RN 0.83 APIs used (`Pressable` function-style
  `style`, `accessibilityState.busy`, `role`, `hitSlop`, `I18nManager`) all
  exist in RN 0.83; React 19.2 ref-as-prop is fine.
- `className` styling works through uniwind — no shim needed. This removes
  the biggest expected blocker (the repo's Tailwind-v4/Uniwind styling
  contract) for every component that only needs className + RN primitives.

Not attempted / expected to need work:

- Anything importing `zustand` (`Select`, `TabBar`, `Toolbar`, most of
  `shell/`) — zustand is pure JS and probably works, but was out of scope.
- `.native.tsx` files (`NativeSeekBar`, `DropZone`, `FilePicker`,
  `semantic.native`, `FileImportExportSheet`) import `@expo/ui` —
  iOS/Android-only at SDK 55; there is no `@expo/ui` macOS target. These
  need Spark-native (`spark-ui`) replacements or labeled RN fallbacks.
- `react-native-gesture-handler`, `react-native-skia`,
  `expo-linear-gradient`, `expo-drag-drop-content-view` peers — native
  modules; the prebuilt Spark Runner only contains Spark's own module set,
  so anything needing them requires a custom `spark build --dev` runtime.
- `@nyc-tron/core` peer — not needed by the four ported files.

## 5. Honest limits

- **Dev Runner only.** Evidence is `spark dev` + prebuilt unsigned Spark
  Runner, Fast Refresh, dev bundle. No `spark build`, signing, notarization
  or `.app` packaging (disk was ~5 GiB free; out of scope).
- **RN-view components, not AppKit controls.** The four NYC-Tron components
  are the package's RN presentational layer — on macOS they render as RN
  views inside the AppKit window. What is genuinely AppKit here is the
  *host*: Spark Runner window chrome, menus, and the `spark-ui`
  `NSSegmentedControl` shown alongside. Do not record this as evidence that
  NYC-Tron controls are AppKit-native; the native-adapter work (M1-c) still
  has to decide per control whether it gets a `spark-*`-style native module
  or a labeled RN fallback.
- **Spark is experimental** ("not ready for production use"), macOS 14+ ARM64.
- **Uniwind on Spark is unverified upstream** — it worked here on Expo 55 /
  RN 0.83 metro, but Spark's `expo-desktop-metro-config` + `withDesktop`
  wrapper is a custom pipeline; pseudo-classes (`active:`, `focus-visible:`,
  `forced-colors:`) compile but their runtime behavior on macOS is
  unexercised. `forced-colors:` variants almost certainly no-op.
- **RN 0.83 vs repo 0.88 divergence stands.** These sources compiled against
  0.83; nothing here proves they run on the Expo 58 host, and nothing in the
  Expo 58 host can run on Spark. Isolation remains mandatory.
- AX verification used System Events on `SparkRunner` (granted to the
  controlling terminal); no NSAccessibility dump from inside the app.
- Disk: ~830 MB transient (two node_modules trees + lockfiles), reclaimed
after capture; committed spike is ~10 MB including `spark-packages/*.tgz`
vendored release inputs. `~/.spark` Runner cache retained per M1-a.

## 6. Recommended next steps (M1-c inputs)

1. The port recipe is proven: vendor-or-subpath the pure-RN components,
   uniwind for className, app-owned `@theme`. A `spark-host` example app in
   the repo (own lockfile, like this spike) could become the permanent M-1
   host rather than growing inside `examples/`.
2. For shell work: Spark ships `ui/sidebar` + `windows/macos` toolbar ops —
   the M1-b shell slice can be built entirely from `spark-ui` native
   controls while NYC-Tron content components stay RN-view.
3. Decide the fallback policy now: any component needing
   gesture-handler/skia/@expo/ui either gets a Spark native module or is
   explicitly labeled RN-fallback in `platformEvidence` notes — never
   claimed native (AGENTS.md rule 3).
4. Track upstream: uniwind×Spark compatibility and a Spark SDK line that
   could ever meet RN 0.88 would collapse the isolation requirement.
