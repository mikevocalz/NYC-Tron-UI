# NYC-Tron UI

NYC-Tron UI is an independent UI library for React Native 0.88 and Expo SDK 58:
iOS, Android and web, plus isolated Windows (React Native Windows 0.85) and macOS
(Spark) adapters. Every component has its own package subpath. The consuming
app owns the theme, fonts, density, motion and state; the library ships no
palette. The current release is a prerelease shipped as GitHub Release
tarballs, not npm.

## Read first

Read only what the task needs. Do not load the whole corpus.

1. `llms.txt` at the repository root: rules plus one link per component group.
2. One group file under `llms/` (for example `llms/ui-forms.txt`): import,
   props, minimal example, accessibility notes, stability proposal and
   platform statuses for each component in that group.
3. `registry/components.json` when you need data rather than prose. Look an
   export up by `symbol`, `importPath` or `id`; the shape is in
   `registry/schema.json`. For example:
   `jq '.items[] | select(.symbol == "TextField" and .preferred)' registry/components.json`
4. `llms/guides.txt` for installation, theming, platform support, migration
   and versioning.

`llms-full.txt` holds everything in one file (about a megabyte). Search it;
do not read it whole. All of these files are generated by
`node tooling/llms.mjs --write` from `docs/library/components.json` and the
documentation catalog. Never edit them by hand.

## Install

Packages are not on npm. Follow README, "Installing from a release": one
`npm install --allow-remote=all <tarball URLs>` command with the core and UI
tarballs from the same release. Add other `@nyc-tron/*` tarballs only for
packages you import. In `@nyc-tron/ui`, every peer other than `react` and
`react-native` is optional and needed only by the subpaths that import it
(for example `zustand`, `@tanstack/react-table`, `react-native-gesture-handler`,
`react-native-skia`, `@expo/ui`). Do not use `--legacy-peer-deps` to hide a
peer mismatch. The Windows packages sit on the React Native 0.85 lane and
cannot share an app with the 0.88 packages.

## Import one component per subpath

```tsx
import { Button } from "@nyc-tron/ui/components/Button";
import { TextField } from "@nyc-tron/ui/components/TextField";
import { Dialog } from "@nyc-tron/ui/components/overlays/Dialog";
import { WaveformLane } from "@nyc-tron/ui/components/forge/WaveformLane";
```

- Use the exact `import` string from the registry item or group file.
- Never import from a package root (`@nyc-tron/ui`, `@nyc-tron/expo-controls`,
  `@nyc-tron/native-controls` ...) when a subpath exports the same component.
  Registry items with `"preferred": false` are such barrel exports; use their
  `preferredId`.
- Professional controls live under `@nyc-tron/ui/components/forge/`. They are
  optional and need no document or editor engine.
- Pure layout policies come from `@nyc-tron/core/<subpath>`
  (`navigation`, `folds`, `pane-plan`, `theme` ...), not from UI components.

## Theme with semantic tokens

- Components style themselves with Tailwind v4 + Uniwind utilities over
  semantic variables: `bg-primary`, `text-on-primary`, `bg-surface-raised`,
  `bg-surface-sunken`, `border-border`, `text-text`, `text-text-muted`,
  `ring-focus`, `rounded-control`, `rounded-card`, and the optional
  `danger`, `on-danger`, `accent`, `info` and `success` tones.
- The app defines every variable for light and dark in its own theme CSS and
  adds an `@source` line for the installed component output (README,
  "App-specific Tailwind v4 / Uniwind styling"). The full list is
  `docs/THEME_TOKENS.md`. A missing variable does not fail the build; the
  utility silently paints nothing, so check both appearances.
- Customise through `className`, the documented class slots
  (`labelClassName`, `iconClassName` ...), `unstyled` where offered, and normal
  React Native styles.
- `themeCssVariables(theme)` from `@nyc-tron/core/theme` returns the
  variables for a validated theme object.

## State

- Keep app and component state in Zustand stores and pass values and
  callbacks in through props; keep resources (players, native handles) in
  refs. Do not add `useState` for new app state.
- Controlled components (`value` with `onValueChange`, `selected` with an
  `onSelect`-style callback) leave the source of truth in your store. The
  examples in the group files show the minimal controlled data.
- Keep product state, media sessions and the app-authored navigation
  selection above layout wrappers, so resizing or re-docking a pane does not
  reset them.

## Accessibility

- Give every interactive control a meaningful accessible name. Keep focus
  order, keyboard activation, text scaling, high contrast, RTL and reduced
  motion working.
- Follow the accessibility notes on each component. "Source-declared roles"
  come from reading source, not from assistive-technology output; verify the
  role, name and value in the mounted app.
- Keep the visible label associated with fields, announce value and
  validation changes, and offer a non-drag alternative for scrubbers, sliders
  and knobs.
- Hide decorative graphics from assistive technology; give meaningful icons
  a text alternative.

## Platforms and stability: report only what is recorded

- `stability.label` is `null` and `ownerConfirmation` is `pending` until the
  owner confirms labels. `stability.proposed` is a proposal, not a promise.
- A platform status of `supported` or `struck` cites a recorded measurement
  (`platformEvidence`). `not verified` means no measurement. Do not describe a
  component as tested on a device, screen reader or headset unless you ran
  that test yourself, and report source checks separately from device runs.
- Native adapters (SwiftUI, Jetpack Compose, WinUI, AppKit) need a
  development build of the host app; Expo Go does not include them.

## Do not

- Import a package-root barrel when a subpath exists.
- Hardcode colors, hex values or a palette; use the app's semantic tokens.
- Write raw HTML UI (`div`, `button`, `input`) or a parallel styling stack;
  use the library components and React Native primitives.
- Copy component source into the app; import the package subpath.
- Add a second pane, inspector or navigation implementation next to the
  library's.
- Store new app state in `useState`; use Zustand.
- Claim a stability label, platform support or accessibility result that
  the registry does not state.

## When you are done

1. Typecheck the app (`tsc --noEmit` or the project script) and run its tests.
2. Check that every new import is a subpath import that exists in
   `registry/components.json`.
3. Report the commands you ran with their results, and list anything you could
   not verify, such as a device or screen-reader run.
