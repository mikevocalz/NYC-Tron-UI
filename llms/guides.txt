## Getting started (getting-started)

Install one component, connect your theme and read the evidence for your target platform.

### Start with your app

NYC-Tron is an independent UI library for React Native and Expo. It ships general app components. Import only the pieces you need. Editor controls such as faders, timelines and color pickers live in Nitro Forge’s @nitro-forge/editor-controls, which builds on Tron.

The current release is v1.0.0-rc.2. The new stable/preview list is a proposal awaiting owner confirmation. A passing install or source check does not certify every component on every platform.

- Installation: the "installation" guide in llms/guides.txt
- Browse components: the component index in llms.txt

### Choose a contract

Each component page names the public import, generated props, example, accessibility notes, proposed stability and measured platforms. Aliases remain visible. Native-only controls retain their host requirements.

## Installation (installation)

Add the published core and UI tarballs to a new or existing Expo app with one install command.

### Create an app

If you already have an Expo app, skip creation and run the install command from its root. Keep the existing runtime, navigation and window contract.

```
npx create-expo-app@5.0.0 my-app --template blank-typescript
cd my-app
```

### Install the release

npm 12 requires --allow-remote=all for remote tarballs; npm 11 ignores the flag. Use npm for these URLs rather than expo install: the tested Expo CLI path rejects remote URLs. The command updates package.json and the npm lockfile.

Core and UI are enough for Button. Some components need optional peers; inspect their import and platform notes before adding them.

```
npm install --allow-remote=all \
  https://github.com/mikevocalz/NYC-Tron-UI/releases/download/v1.0.0-rc.2/nyc-tron-core-1.0.0-rc.2.tgz \
  https://github.com/mikevocalz/NYC-Tron-UI/releases/download/v1.0.0-rc.2/nyc-tron-ui-1.0.0-rc.2.tgz
```

### Render Button

Copy this exact example to App.tsx. It introduces no React state. Your consuming app owns fonts, colors, radius and density. Connect the semantic tokens in the theming guide before treating this as your production styling.

```
import { Button } from "@nyc-tron/ui/components/Button";

export default function App() {
  return <Button title="Hello" onPress={() => {}} />;
}
```

### Run your target

A development build is required for native modules that Expo Go does not include. Core UI components do not by themselves prove a native adapter is installed or measured.

If npm reports ERESOLVE, compare the app runtime and optional peer ranges with the support guide. Do not use --legacy-peer-deps to hide a mismatch.

```
npx expo start
# For web, add the Expo-compatible web peers first:
npx expo install react-native-web react-dom
npx expo start --web
```

## Theming (theming)

Keep the consuming app in charge of colors, fonts, radius, density and motion.

### Connect the existing styling path

Resolve @source from the location of your own stylesheet. The library does not load a global NYC-MON palette or replace the app theme. Native adapters map supported semantic values to platform resources; arbitrary CSS utilities are not a native-control API.

```
@import "tailwindcss";
@import "uniwind";
@import "@acme/theme/theme-native.css";
@source "../node_modules/@nyc-tron/ui/dist/components";
```

### Define semantic variables

These are example app values, not a library brand. Define light and dark values through your Tailwind/Uniwind runtime. Test every text, focus and control-boundary pair in your own palette. Missing optional tokens can leave a recipe uncolored without a build error.

The reference border in the older token guide is 1.58:1 and is unsuitable when it is the only visible input boundary. This example uses a stronger border; it is still your responsibility to verify the complete control and its states.

```
@theme {
  --color-primary: #1f5fd1;
  --color-on-primary: #ffffff;
  --color-surface-raised: #ffffff;
  --color-surface-sunken: #f1f3f6;
  --color-border: #7a8799;
  --color-text: #15181d;
  --color-text-muted: #5a626e;
  --color-danger: #b42318;
  --color-on-danger: #ffffff;
  --color-accent: #1f7a6d;
  --color-info: #1d5fa8;
  --color-success: #1e7a3c;
  --color-focus: #1f5fd1;
  --radius-control: 8px;
  --radius-card: 12px;
}
```

## Platform support (platform-support)

Separate component stability from evidence for a runtime, platform and interaction.

### Proposed library tiers

Tier 1: iOS simulator, Android emulator and web. Every confirmed stable component must pass its individual library evidence packet before stable publication.

Tier 2: publish the measured component lists for Spark macOS and React Native Windows. Their host versions remain isolated and below UI’s React Native peer floor. Use the documented scoped override and only the lane’s support list.

Tier 3: visionOS, Quest, PICO and physical-hardware scenarios are not verified for 1.0.0. This includes pen/palm, fold postures, screen-reader speech and multi-display.

### Read a platform badge

Supported means a recorded measurement exists for that named import in the cited lane. Struck means the lane measurement failed it. Not verified means there is insufficient evidence. None of these badges approves a stability proposal.

Historical D5 measurements retain their rc.1 archive, date and graph. They are not fresh rc.3 evidence. Native compilation, source tests, web rendering and screen-reader speech are separate claims.

- Exact runtime lanes and desktop support lists: https://github.com/mikevocalz/NYC-Tron-UI/blob/main/docs/SUPPORT.md

## Migration (migration)

Move between candidates: the editor-control import change, app state and platform contracts.

### From rc.2 to the standalone library candidate

Breaking: the owner moved the editor controls to Nitro Forge (decision D10, 2026-11-28). Replace each @nyc-tron/ui/components/forge/<path> import with @nitro-forge/editor-controls/<path>. The three precision helpers stayed in Tron: components/forge/inputs/precision, precision-scrubber-model and PrecisionScrubber are now components/shell/precision, precision-scrubber-model and PrecisionScrubber. docs/library/editor-controls-migration.json lists every removed subpath with its replacement. Every other public import path is unchanged.

Compare generated API snapshots, manifests and release checksum files before upgrading. Install the exact candidate’s core and UI archives together. Keep desktop adapter archives from their independently tested lanes.

Your app’s Zustand stores, imperative refs, authored navigation shell, window dimensions and XR scene geometry remain yours. An upgrade is not permission to change them.

### Deprecations

Existing theme aliases remain accepted. A deprecation must name its replacement and migration path before removal. Stable API removal or type changes require a major release and an owner decision. Preview changes must be labelled in release notes.

## Versioning policy (versioning)

Define the public contract before making a stability promise.

### Stable components

A confirmed stable API is covered by Semantic Versioning: compatible fixes are patches; compatible additions are minors; removals, renames, incompatible types or behavior require a major. Broader support claims require their own evidence.

Stable labels are not yet confirmed in the current proposed manifest. A label alone cannot satisfy release evidence.

### Preview components

Preview is an explicitly experimental API outside the stable component promise. It may change in a minor only when clearly labelled preview in the manifest, docs and changelog. Announce the old and new contract with a migration example.

Preview does not mean inaccessible, undocumented or safe to claim on unmeasured platforms. Preserve compatibility where practical and document all changes.

### Deprecation and distribution

Announce deprecation before removal, retain the old import where compatible and explain migration. Package versions remain synchronized across release archives. The owner approves any public export removal, rename or type change.

- Semantic Versioning 2.0.0: https://semver.org/

## Contributing (contributing)

Add a component, its documentation and evidence in one reviewable change.

### Extend the existing owner

Read AGENTS.md, the public API snapshots and existing component before adding another abstraction. Reusable UI belongs in NYC-Tron; document engines remain in their owning applications. Never import @nitro-forge into Tron.

Use Zustand for component/app state and refs for resources. Keep app-owned semantic tokens and existing platform/window contracts.

### Update the inventory and docs

Add or update the independent package subpath, declarations, meaningful tests, component example and accessibility notes. Regenerate snapshots only while reviewing the API diff. Every public symbol must be classified; a new component must enter the manifest and docs.

Propose a stability label with a reason; the owner confirms it. A stable target needs unit/model, rendered web, installed-tarball iOS/Android, static accessibility and documentation evidence. Do not mark an unrun check passed.

```
pnpm build
node tooling/api-surface.mjs
node tooling/api-signatures.mjs
node tooling/library-components.mjs --write
npm --prefix website ci
npm --prefix website run build
npm --prefix website test
```

### Review

Open a draft PR with skill outputs, actual command/CI evidence and independent reviewer findings. Preserve licenses and dated proof. Do not merge or mark ready on the owner’s behalf.

## Distribution proposal (distribution)

Keep GitHub Release tarballs for 1.0.0 while the owner considers npm separately.

### Recommendation

Retain GitHub Release tarballs for 1.0.0. All sixteen distributable packages are private, and current gates enforce that contract. npm distribution is an owner decision; this proposal publishes nothing.

### What npm would require

Confirm scope/package availability and publishing access; complete licensing and source-availability review; settle peer-range policy and supported runtime claims.

Coordinate private flags, package versions, dist-tags, provenance, release automation and rollback across sixteen packages. Preserve the exact independently tested desktop archives. Add clean npm consumers for each supported lane before claiming the path works.

Only the owner’s exact version/checksum GitHub comment satisfies stable distribution approval. These docs do not alter that record.
